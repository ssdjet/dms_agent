# Разработка и тестирование

## Окружение

- Python 3.10+.
- Runtime-зависимости задаются в `pyproject.toml`.
- Набор разработки устанавливается командой:

```powershell
python -m pip install -e ".[test]"
```

Опциональная группа `test` добавляет `pytest` и `xlwt`. `xlwt` нужен только для
создания синтетических `.xls` книг в тестах; он не требуется для чтения
пользовательских файлов в runtime.

## Быстрые проверки

```powershell
python -m pytest -q
python -m compileall -q dms_pipeline tests
python -m pip check
node --check dms_pipeline/static/app.js
git diff --check
```

Успешный `pytest` не заменяет проверку актуальности справочников, корректности
колонок или утверждения бизнес-политики.

## Что покрывают тесты

`tests/test_pipeline.py`:

- SHA-256 и чтение синтетических `.xlsx`/`.xls`;
- сохранение номера строки при пропуске пустой строки;
- выбор листа, обязательные и дублирующиеся заголовки, неподдерживаемые
  расширения и некорректная конфигурация;
- mapping, обязательные поля, допустимые значения, тип суммы, верхнюю границу,
  статусы `not_evaluated` и сериализацию аудита без содержимого записи;
- сквозную цепочку read → map → rules → audit на искусственной книге.

`tests/test_web.py`:

- раздачу локального HTML/JS/CSS и security headers;
- ответы inspect/analyze;
- безопасное отсутствие значений строки в JSON;
- многолистовую книгу и невалидные пользовательские поля;
- удаление временной загруженной книги после завершения запроса.

Фикстуры генерируются в памяти/временном каталоге и содержат только явно
искусственные значения. Никогда не используйте прикреплённые книги или
реальные реестры как fixtures.

## Соглашения кода

- Следуйте стилю существующих модулей: небольшие модули по ответственности,
  типы на публичных границах, dataclass для неизменяемой конфигурации/результата.
- Ожидаемые ошибки представляются типами из `errors.py`; не скрывайте ошибки
  `except Exception` или значениями по умолчанию.
- Проверки остаются детерминированными и не используют сеть/часы/случайные
  данные.
- Новое правило возвращает только статический `rule_id`, статус и сообщение;
  сообщение не должно встраивать проверяемое значение.
- Добавляйте тест для граничных состояний, ошибок ввода и privacy-поведения
  каждой новой поверхности.
- Сохраняйте границу политики: изменение вычислительного механизма не должно
  самовольно менять справочник, предел или решение о покрытии.

## Добавление нового правила

1. Сформулируйте точное техническое условие, ожидаемые типы данных и поведение
   при отсутствии поля/настройки.
2. Реализуйте небольшой класс или функцию правила, которая принимает запись и
   возвращает `RuleResult`; не сохраняйте запись и не добавляйте значения в
   сообщение.
3. Определите, должно ли незаданное значение давать `not_evaluated`, и
   согласуйте поведение с caller.
4. Подключите правило в `build_rules()` только при явной конфигурации.
5. Если правило доступно в веб-интерфейсе, добавьте его форму, статическую
   подпись и документацию, сохранив серверную валидацию.
6. Покройте pass, fail, отсутствующее/некорректное значение, неустановленный
   справочник/лимит и отсутствие исходных значений в аудите/API.

## Релизная дисциплина

Проверяйте `git status`, `git diff --check` и содержимое включаемых файлов.
Реальные или обезличенные рабочие книги, временные файлы, тестовые выгрузки и
локальные конфигурации не должны случайно попасть в коммит. Не коммитьте
решения о покрытии или production-политики без подтверждённых источников и
обзора соответствующих владельцев.
